# Android integration contracts

Reviewed against the repository at TASK-002 and official sources accessed 2026-11-28. This is an implementation contract, not evidence of physical reliability or Google Play approval. The [approved design](../.roadmap/DESIGN.md) governs future behavior; [physical testing](PHASE_1_TESTING.md) and [scheduling testing](SCHEDULING_TESTING.md) retain outstanding observations.

## Monitoring and presentation

**Current.** The main manifest declares the exported accessibility service protected by `BIND_ACCESSIBILITY_SERVICE`; this is a binding restriction on the service, not a permission requested by the app. The service configuration requests window-state and windows-changed events, interactive windows and window-content access, and sets `isAccessibilityTool=false`. `AppMonitorService` observes focused/active window package metadata, ignores its own overlay, and does not inspect node text or children. Android binds an enabled accessibility service and delivers configured events; events and windows are observations, not a guarantee of an instantaneous or complete foreground history. [AccessibilityService](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService), [AccessibilityEvent](https://developer.android.com/reference/android/view/accessibility/AccessibilityEvent).

`BlockController` adds a full-size, clickable `TYPE_ACCESSIBILITY_OVERLAY`, with `FLAG_NOT_FOCUSABLE`, Home and accessibility-settings actions. A connected service can use this window type to intercept interaction; this does not disable the target app. Android describes touchable accessibility overlays separately from `TYPE_APPLICATION_OVERLAY`, which requires `SYSTEM_ALERT_WINDOW` and user authorization. The main manifest requests neither that permission nor usage access; the debug manifest requests Internet for Metro only. No permission is added by this task. [Window types](https://developer.android.com/reference/android/view/WindowManager.LayoutParams#TYPE_ACCESSIBILITY_OVERLAY), [application overlay permission](https://developer.android.com/reference/android/Manifest.permission#SYSTEM_ALERT_WINDOW).

**Selected future mechanism.** Native emergency controls belong on the existing accessibility surface and must use authoritative native state, including when React Native is closed. Maintain usable Home, Settings, revocation and uninstall paths; surface presentation failure as unavailable. Focus, touch, system navigation, split screen and manufacturer behavior must be checked physically; the API description does not prove those paths work on every device.

## Time, recovery and lifecycle

**Current.** `AndroidOverrideClock` samples `elapsedRealtime()` and `Settings.Global.BOOT_COUNT`; missing, security-denied or negative boot counts become an `IOException`. `elapsedRealtime` is monotonic since boot and includes deep sleep; `BOOT_COUNT` was added in API 24 and is readable as a global setting. A count identifies the boot context for this design, not a durable session identity, and a read failure must not authorize access. [SystemClock](https://developer.android.com/reference/android/os/SystemClock#elapsedRealtime()), [BOOT_COUNT](https://developer.android.com/reference/android/provider/Settings.Global#BOOT_COUNT).

The service refreshes on connection and window events, with main-looper callbacks nominally every 250 ms while blocking and 1 s otherwise, plus bounded recovery retries; it cleans up on unbind/destroy. `Handler.postDelayed` uses uptime, excludes deep sleep, and may never execute if its looper exits. Thus elapsed deadlines can pass asleep without a callback at the deadline. A reconnect or subsequent observation must re-evaluate; none of these intervals is a wakeup or latency guarantee. [Handler](https://developer.android.com/reference/android/os/Handler#postDelayed(java.lang.Runnable,%20long)), [AccessibilityService lifecycle](https://developer.android.com/reference/android/accessibilityservice/AccessibilityService).

**Selected future mechanism.** Recover and revalidate native state on service connection and relevant commands/status reads. Use current local time and zone for morning windows; use same-boot elapsed time for emergency wait/access. Reboot cancels pending access and ends grants while preserving completed usage. TASK-003 must attach identity to the captured frozen session, including rollback/re-entry, rather than deriving it from a returned date or boot count. Clock changes remain an accepted morning-window bypass.

No boot or time receiver currently exists or is assumed necessary. Consider a narrowly scoped boot, time or time-zone receiver only after a measured gap and verification of its registration, permission and delivery constraints. Android restricts background broadcasts and can defer delivery; `BOOT_COMPLETED` is an exception to implicit broadcast restrictions and requires `RECEIVE_BOOT_COMPLETED` if adopted. A receiver is not a guaranteed real-time wakeup, and cannot enable a disabled accessibility service or promise recovery after force-stop. [Broadcasts](https://developer.android.com/develop/background-work/background-tasks/broadcasts), [broadcast exceptions](https://developer.android.com/develop/background-work/background-tasks/broadcasts/broadcast-exceptions), [boot permission](https://developer.android.com/reference/android/Manifest.permission#RECEIVE_BOOT_COMPLETED), [stopped packages](https://developer.android.com/reference/android/content/Intent#FLAG_EXCLUDE_STOPPED_PACKAGES).

## Storage and package visibility

**Current.** Policy and emergency records use separate Preferences DataStore files (`morning_policy` and `emergency_access`); emergency state is not yet integrated with enforcement. DataStore provides atomic read-modify-write for a single stored object, not a transaction spanning these files or future Room history. [DataStore](https://developer.android.com/topic/libraries/architecture/datastore).

**Selected future mechanism.** Preserve the captured session identity and completed-use ledger across migration and reopen. Coordinate separate stores without nested reverse locks, re-sample and revalidate after suspended work, and fail conservatively on storage, schema or clock errors. Future Room history is an app-private event record, not authorization; delivery requires idempotent retry because a DataStore transition and Room insert cannot be claimed atomic together. Store only necessary local event metadata; do not read other apps' message text or screen content. [Room](https://developer.android.com/training/data-storage/room), [app-specific storage](https://developer.android.com/training/data-storage/app-specific).

The current manifest has no `<queries>` or `QUERY_ALL_PACKAGES`: the fixed supported package catalog does not require installed-app discovery. Android filters package-information queries for apps targeting API 30 or higher; if later discovery needs visibility, first evaluate specific `<queries>` entries rather than broad visibility. [Package visibility](https://developer.android.com/training/package-visibility), [declaring specific packages](https://developer.android.com/training/package-visibility/declaring).

## Disclosure and distribution

**Current.** Setup explains foreground package/window metadata, local use and the blocking surface, says emergency access is unavailable, and offers an affirmative settings action. It tells users they can disable the service or uninstall. The service configuration declares `isAccessibilityTool=false`; this personal wellbeing product is not represented as a disability-support tool.

**Distribution boundary.** Google Play restricts the accessibility-tool designation to qualifying disability-support services. Its policy for other accessibility API uses requires an accessibility declaration, a separate prominent in-app disclosure describing access and use, and affirmative consent; it also prohibits obstructing disabling/uninstalling in this product's context, bypassing platform controls and deceptive UI. Review the actual final implementation, consent flow, listing and current policy before any submission; the present disclosure is not a finding of eligibility or approval. [Accessibility API policy](https://support.google.com/googleplay/android-developer/answer/16558241), [AccessibilityService guidance](https://support.google.com/googleplay/android-developer/answer/10964491), [disclosure guidance](https://support.google.com/googleplay/android-developer/answer/11150561).

No device was tested in this task. Process death, reboot, sleep, clock/zone changes, permission revocation, multi-window and foreground grant expiry remain subject to the documented physical matrix; existing user reports and the Phase 1 continuation decision do not establish those results.
